# Conformance-Checking Experiment Platform — Task Design Reference

Derived from `Tasks Overview` (cols B/C/D = task identity, E = concat, G = description) in
`Conformance_Checking_Tasks_final_v02.xlsx`. Grounded against `BPIC12_Log_onlyA.csv`
(XES-style log: `case:concept:name`, `concept:name`, `org:resource`, `time:timestamp`,
`case:AMOUNT_REQ`) and `Model_A.bpmn` (10 tasks, 5 XOR + 2 AND gateways). The tooling below
is dataset-agnostic: it consumes *any* XES/CSV log + BPMN/PNML model, so the platform generalises.

---

## 1. Design framework

### 1.1 Answer-format catalogue (maximise formats, minimise answer variation)

Each format has **one** canonical entry rule so a string-equality / set-equality check decides correctness.

| Format | Use when | Canonical entry rule (what we tell the participant) |
|---|---|---|
| `pct` (scalar %) | fitness, share-of-traces, per-rule conformance | Integer percent with sign, rounded to nearest whole number: **`96%`** (never `0.96`, `96.1%`). |
| `count` (scalar int) | frequency / number of occurrences | Non-negative integer: **`42`**. |
| `decimal` (scalar) | correlation, coefficients | Two decimals, leading zero: **`0.42`** / **`-0.18`**. |
| `pct-set` / `count-set` | one value per entity (per sublog / per time-bin / per rule) | Fixed, pre-labelled rows; each cell follows `pct`/`count` rule. Sum-to-100% enforced for distributions. |
| `mc-single` | one correct option (incl. Yes/No, ordinal severity) | Radio buttons; exactly one selection. |
| `mc-multi` | "select all that apply" over a **closed** set (activities, constraints, rules, columns, pairs) | Checkboxes over the platform-generated option set; graded as set equality. |
| `rank` | top-N / ordering of a given set | Drag-to-order over the supplied items. |
| `matrix` | co-occurrence / pairwise grids | Toggle grid; graded as the set of selected cells. |
| `free-text` | genuinely interpretive answers (reasons, severity judgement, pattern prose) | Open box; **not auto-graded** — scored against admin reference/rubric. |

**Design rule applied throughout:** whenever a task *description* is phrased openly ("identify",
"describe", "summarize") but the underlying artefact is a discrete, computable set (which activities
are skipped, which constraints break, which traces are non-conformant), the format is pushed to
`mc-multi` / `rank` / `matrix` so the answer becomes checkable. Free-text is reserved for the part
that is irreducibly a judgement.

### 1.2 Ground-truth computability tiers

- **AUTO** — fully computable from (log + model) with no human parameter. Platform generates the ground truth.
- **SEMI** — computable *once the admin supplies one parameter* (a condition, threshold, split attribute,
  time-binning, rule set, technique, severity map). After that the ground truth is deterministic.
- **MANUAL** — irreducibly subjective. Admin supplies a reference answer / rubric; platform may still
  auto-compute a *supporting* artefact (e.g. correlations, deviation profile) to help the admin write it.

### 1.3 Tooling stack

- **pm4py** — import BPMN (`pm4py.read_bpmn`) → Petri net (`pm4py.convert_to_petri_net`);
  `fitness_alignments` / `fitness_token_based_replay` (log + per-trace fitness);
  `conformance_diagnostics_alignments` (per-trace **move-on-log** = inserted activities,
  **move-on-model** = skipped activities — the raw material for every violation/identification task);
  `conformance_declare`/footprints for declarative & model-vs-model comparison.
- **pandas** — sublog filtering by case/event attribute, `value_counts` (frequencies), `cut` (conformance
  bins / time windows), `crosstab` (co-occurrence), distribution comparison between sublogs.
- **scipy / statsmodels** — `pointbiserialr` / `pearsonr` for conformance-vs-outcome correlation.
- **lifelines** — survival / positive-outcome-probability-over-time (the "impact on outcome" task).
- **Declare4Py / RuM** — LTL / Declare per-rule conformance when guidelines are declarative rather than a BPMN.

> **Note on "guidelines" format** (open question flagged in the sheet, tasks #1/#26): the platform should
> accept guidelines in **two** representations — (a) an imperative model (BPMN→Petri net) for
> alignment-based tasks, and (b) a declarative rule set (Declare/LTL) for per-rule tasks (task #36, and
> optionally #9/#11). Tasks that say "in the model" (#35, #26) presuppose representation (a).
